# Proposal

## Why

现有 Agent 的 `write_wiki_document` 要求用户提供真实 `spaceId`，且只能将文档写到空间根目录。用户无法通过自然语言稳定完成“找到可写空间、建立任务文件夹、保存文档”。同时，页面写操作与 Agent 写操作分别使用“可见”和“可编辑”判断，公开空间的行为不一致，团队只读成员可能通过部分页面入口修改内容。

## What Changes

- 为 Agent 增加只读的可写空间与文件夹查询工具，返回当前登录用户有权写入的空间、文件夹名称及字符串 ID；未指定空间时默认个人空间，明确提及团队名称时只在唯一匹配后继续。
- 为 Agent 增加独立的创建文件夹和创建文档工具。每次新内容写入先建立“任务内容＋日期”文件夹，再在其中创建文档；服务端完成名称规范化、同名顺延和写入时的二次权限校验。
- 预置文档写入流程 Skill，指导 Agent 按查询目标、处理歧义、创建、核对结果的顺序调用工具；数据库写入规则由 Cloud 代码执行。
- 新增带 `isWrite` 参数的空间与文件夹访问检查。读操作沿用现有可见性规则；写操作要求空间编辑权限，其中公开空间对任何已登录用户可写，团队空间仅管理员或编辑可写，个人空间仅所属用户或平台管理员可写。
- 将现有页面的文档、文件夹和回收站写入口统一到写权限检查。既有读取、预览、搜索范围保持不变。

## Capabilities

### New Capabilities

- `agent-wiki-write`: Agent 查询当前用户的可写目录、解析目标空间并按固定规则创建任务文件夹和文档，使用预置流程 Skill。

### Modified Capabilities

- `wiki-space`: 明确空间级读写权限以及公开空间对已登录用户的写权限。
- `wiki-folder`: 创建、重命名、移动、逻辑删除及回收站写操作按空间写权限判断。
- `wiki-document`: 新增、编辑、删除及移动文档按源与目标空间写权限判断。
- `wiki-recycle-bin`: 恢复和永久删除按回收站记录真实所属空间的写权限判断，回收站列表仍按可见权限读取。

## Impact

涉及 `cloud` 的 Wiki 权限与 Agent 内部接口、`cloud_agent` 的工具注册及循环提示、Agent Skill 目录接入、相关页面操作状态和测试。对现有团队只读成员属于**BREAKING** 权限收紧：仍可读取，但不能再通过页面写入口操作团队内容。公开空间内任意已登录用户可以操作其他用户创建的文件夹和文档；`DocumentWiki.userId` 继续记录创建者，不作为公开空间的所有权限制。此次不实现 Agent 检索、修改、删除、手选引用和联网搜索。回滚时撤销本变更的工具、Skill 与写权限入口变动，不迁移或删除已有 Wiki 数据。
