# 设计：boost-rag-passage-recall

## 1. 问题定义与口径

| 项 | 值 |
| --- | --- |
| 指标 | `recall@6`（切片级召回：前 6 条命中的 gold 切片数 ÷ 该题 gold 切片总数），399 题宏平均 |
| 基线 | **0.5623**（`eval/results/baseline-20260915-091440-http.json`） |
| 本分支复跑 | **0.5636**（同数据同口径重跑，Δ0.13pt —— 与既有"重跑极差 0.13pt"一致，基线可信） |
| 目标 | **≥0.85** |
| 被测接口 | `POST /api/open/rag/search`（`fetchK=10`，本地截断算各 K） |
| 语料范围 | 政策空间 `2095544464810774531`：216 篇 / 2061 个 ACTIVE 切片 |

## 2. 证据链：0.85 在哪里，以及为什么现在的路走不到

### 2.1 上限不是 1.0

很多题的 gold 本身就有十几到三十几段（B-06 有 33 段 gold），而只有 6 个槽位
→ 完美排序下 `recall@6` 的数学上限只有 **0.9783**（`recall@3` 0.9455、`recall@10` 0.9901）。
所以 0.85 相当于**吃掉全库可用空间的 86%**。

### 2.2 候选池决定天花板

重排只负责「从候选里挑 6 个」，所以要先看候选池里到底有没有 gold。用 `topK=200` 深取一轮（`eval/tmp/diag-rankings.json`）：

| 候选深度 N | 纯向量 oracle@N | 向量+BM25 融合 oracle@N |
| --- | --- | --- |
| 6 | 0.5636 | 0.5957 |
| 10 | 0.6347 | 0.6783 |
| 20 | 0.7189 | 0.7690 |
| 30 | 0.7602 | — |
| 50 | 0.8148 | **0.8600** |
| 100 | 0.8532 | **0.9061** |
| 200 | 0.8890 | 0.9288 |

**关键结论**：
- 纯向量池即使给一个完美重排器，`top-50` 只到 0.8148 —— **够不到目标**；
- 补一路 BM25 词法通道后 `top-50` 就到 0.8600、`top-100` 到 0.9061 —— **候选池这一关才算过**；
- 2061 块里有 **16 道题在前 200 条内一段 gold 都没有**，这是纯向量通道的硬盲区。

### 2.3 重排不是免费的

原型实测（同一 399 题，直接把候选池喂给重排模型）：

| 重排方式 | `recall@6` | 吃到多少可用空间 |
| --- | --- | --- |
| 不重排（纯向量 top-6） | 0.5636 | — |
| `gte-rerank-v2` over top-20 | 0.5841 | 8.1% |
| `gte-rerank-v2` over top-50 | 0.5992 | 14.2% |
| `gte-rerank-v2` over top-100 | 0.5999 | **12.5%** |
| 完美重排 over top-100 | 0.8532 | 100% |

`gte-rerank-v2` 在中文公文问答上只吃到 ~12.5%，**单纯"接个重排"无法完成任务**。

### 2.4 病灶定位：文档找到了，段落没排对

126 道恒零题（`recall@6 = 0`）的构成：

| gold 文档在哪 | 题数 | 占比 |
| --- | --- | --- |
| top1 命中的就是 gold 文档 | 29 | 23.0% |
| gold 文档在前 10 内 | 74 | 58.7% |
| gold 文档连前 10 都没进 | 23 | 18.3% |

即 **82% 的恒零题是"文档已找到、段落选错"**；而它们的 gold 段数多为 1~2 段（61+38=99 题），
一旦排序修好就是从 0 直接到 1.0。**12.6 万分的总分里有 31.6 分卡在这一层。**

首个 gold 段的位次分布：1-10 位 34 题 / 11-20 位 28 题 / 21-50 位 30 题 / 51-200 位 18 题 / 200 内没有 16 题。

## 3. 方案

### 3.1 总体链路（改动后）

```
① 权限过滤（不变）
② 文号精确层：命中即【钉位】，且不再吞掉向量检索     ← 修复 2.3 的缺陷
③ 候选生成（并行两路，同一次查询向量复用）
     a) 向量通道：查询向量 × 空间内全部 ACTIVE 块 → top candidatePoolSize
     b) 词法通道：BM25（CJK bigram）→ top candidatePoolSize
④ 融合：RRF，产出混合候选池（去重后 top fusionPoolSize）
⑤ 重排（可选，额度相关）：gte-rerank-v2 对候选池打分 → 截 topK
⑥ 返回 topK（加上限保护）
```

### 3.2 词法通道为什么自己实现而不是用 MySQL FULLTEXT

- 现有 FULLTEXT 建在 `document_wiki(title, content)` 上，是**文档级**且没有 `(docId, chunkIndex)` 坐标，
  与切片级检索的判分坐标对不上；
- 给 `wiki_chunk` 新建 FULLTEXT 索引要 DDL 且 ngram 解析器行为受 MySQL 版本影响；
- **向量库本来就把整个空间的 chunk 载入内存**（`InMemoryCosineVectorStore.loadSpace`），
  在同一份语料上算 BM25 是零额外 IO、零外部依赖的。实测 2061 块、9.1 万词表，单查询毫秒级。

### 3.3 文号精确层为什么必须"钉位"

原型实测：把文号层结果丢进 RRF 融合，B 类 `recall@6` 从 0.6525 **掉到 0.4129**
（融合把 1.0 分的精确命中摊薄了）。而文号层是本系统相对朴素向量的真实增量
（B 类 `docRecall@6 = 1.0000`，纯向量对照仅 0.333）。因此文号命中必须占据前几位，
只在其**内部**重排（用查询向量 + 词法分），而不是与外层候选混排。

### 3.4 失败回退

重排适配器、词法通道都必须是**可失败的非关键路径**：任一环节异常 → 回退到上一层的排序结果并继续返回，
检索接口不得因此报错（与既有 `Index failures never block document operations` 同一原则）。

## 4. 备选方案与取舍

| 方案 | 结论 |
| --- | --- |
| 只加深候选池 + cross-encoder 重排 | **否决**。纯向量池 oracle@50=0.8148 < 0.85，且 gte 只吃到 12.5% |
| 改切块参数 | **否决**。需全量重建 + gold 重对齐，且瓶颈在排序不在切块（`docRecall@6 0.8697` vs `recall@6 0.5623`） |
| 换 embedding 模型 | 未验证。属独立课题，且同样受额度阻塞 |
| MySQL FULLTEXT 做词法通道 | 否决，见 3.2 |
| **向量 + BM25 融合（本方案）** | **采纳**。零模型依赖，候选池 oracle@50 → 0.8600，实测 top-6 +3.2pt，并为重排铺好候选池 |
| 单靠调评测集阈值刷分 | **禁止**。所有阈值只用非评测数据确定 |

## 5. 风险

| 风险 | 处置 |
| --- | --- |
| 融合权重/RRF 常数过拟合评测集 | RRF 常数取文献默认 60，不针对本数据集调参；若需调参，只在 `golden.v1.jsonl` 上调、在 v2 上报 |
| 词法通道在英文语料（MHR 空间）退化 | CJK bigram 规则对英文自动退化为按词切分；英文空间的检索效果单独用 `eval/datasets/mhr-rag/` 验证，不与中文指标混算 |
| 重排引入延迟 | 候选池深度设上限（默认 50），超时即回退 |
| 额度不可用 | 词法与融合不依赖额度；重排位可空转（`enabled=false`） |
