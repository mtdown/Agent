# Proposal

## Why

现有 Agent 的 `write_wiki_document` 要求用户提供真实 `spaceId`，且只能将文档写到空间根目录。用户无法通过自然语言稳定完成“找到可写空间、建立任务文件夹、保存文档”。同时，页面写操作与 Agent 写操作分别使用“可见”和“可编辑”判断，公开空间的行为不一致，团队只读成员可能通过部分页面入口修改内容。

## What Changes

- 为 Agent 增加只读的可写空间与文件夹查询工具，向工具内部返回当前登录用户有权写入的空间、文件夹名称及字符串 ID；未指定空间时展示结构化可写空间选项并推荐个人空间，用户选定后才写入；明确提及团队名称且唯一匹配时可直接继续。
- 在 Agent 对话中使用结构化选择和结构化写入结果：页面只展示空间、文件夹和文档的人类可读名称及操作按钮，不显示原始空间、文件夹、文档 ID；选择动作通过一次性不透明 token 关联内部目标，并在执行前重新鉴权。
- 为 Agent 增加独立的创建文件夹和创建文档工具。每次新内容写入先建立“任务内容＋日期”文件夹，再在其中创建文档；服务端完成名称规范化、同名顺延和写入时的二次权限校验。
- 预置文档写入流程 Skill，指导 Agent 按查询目标、处理歧义、创建、核对结果的顺序调用工具；数据库写入规则由 Cloud 代码执行。
- 新增带 `isWrite` 参数的空间与文件夹访问检查。读操作沿用现有可见性规则；写操作要求空间编辑权限，其中公开空间对任何已登录用户可写，团队空间仅管理员或编辑可写，个人空间仅所属用户或平台管理员可写。
- 将现有页面的文档、文件夹和回收站写入口统一到写权限检查。既有读取、预览、搜索范围保持不变。
- 平台管理员可按 ID 写入但 Agent 可写目录未列出未加入团队空间的差异，按负责人决定暂缓；管理员对他人个人空间的权限边界留待独立任务明确，本次不扩展目录枚举范围。

## Capabilities

### New Capabilities

- `agent-wiki-write`: Agent 查询当前用户的可写目录、解析目标空间并按固定规则创建任务文件夹和文档，使用预置流程 Skill。

### Modified Capabilities

- `wiki-space`: 明确空间级读写权限以及公开空间对已登录用户的写权限。
- `wiki-folder`: 创建、重命名、移动、逻辑删除及回收站写操作按空间写权限判断。
- `wiki-document`: 新增、编辑、删除及移动文档按源与目标空间写权限判断。
- `wiki-recycle-bin`: 恢复和永久删除按回收站记录真实所属空间的写权限判断，回收站列表仍按可见权限读取。

## Acceptance Criteria

- 用户要求写入但未指定空间时，先看到可点击的可写空间选项，「个人空间」为推荐项；点击前没有任何文件夹或文档被创建。
- 明确指定且唯一匹配的可写团队空间可以直接写入；目标含糊时展示候选选项，选定后才执行。
- 创建成功、部分失败、工具错误及历史回放只显示人类可读的名称和路径，不在对话文字中显示空间、文件夹、文档或用户原始 ID；成功的文档可从结果打开。
- 选项 token 只能由对应用户在对应会话内使用一次；过期、伪造、重放或权限变化后不能创建内容。
- 个人空间的旧存储名称 `个人区-<userId>` 不出现在用户界面；空间展示名由类型生成，不增加名称映射表。

## Impact

涉及 `cloud` 的 Wiki 权限、Agent 对话状态和内部接口，`cloud_agent` 的工具注册及循环提示、Agent Skill 目录接入、Agent 对话页面的选项/结果展示和测试。对现有团队只读成员属于**BREAKING** 权限收紧：仍可读取，但不能再通过页面写入口操作团队内容。公开空间内任意已登录用户可以操作其他用户创建的文件夹和文档；`DocumentWiki.userId` 继续记录创建者，不作为公开空间的所有权限制。此次不实现 Agent 检索、修改、删除、手选引用和联网搜索；不新增空间名称映射表。回滚时撤销本变更的工具、Skill、结构化交互与写权限入口变动，不迁移或删除已有 Wiki 数据。
