# Design

## 1. 为什么是阶段派单

**不是继续逐原子任务**：逐原子任务的问题不在运输成本，而在每个任务都要重复一遍八步交接链路（派单、开发、回执、审查、冻结快照、生成差异、新建测试实例、判定），其中只有两步产生代码。往返次数随任务数线性增长。

**也不是砍掉管理者**：管理者的产出物形态可变，但三项职能不可省——

1. **证据链公正性依赖第三方**：开发者自行准备快照与差异时，选出的必然是对自己有利的文件集合；测试者无法确认不利证据是否被包含。快照必须由非实现方冻结。
2. **双向翻译**：开发与测试互相看不到对方推理，必须有人把测试报告翻译成可执行的修复指令、把回执翻译成可验证的快照。
3. 否则负责人成为该第三方，届时负责人既是瓶颈，上下文又被两边污染。

**结论**：改变管理者做什么，而不是决定他做几次。产出物从逐任务卡片改为三件套——阶段简报（一次，重投入）、任务清单文件（验收项与任务 ID 绑定）、阶段末判定表。中间的搬运步骤全部删除，往返从 N 降到 2。

## 2. 为什么阶段门默认不阻塞

阶段门的目的负责人「看得见」，不是每个决定都要负责人批准。若每个阶段都阻塞等待确认，一个 5 阶段的 change 就是 5 次打断，「每阶段开门」本身会成为新的卡顿源——这正是最初抱怨的反面。

因此：**提交简报是默认动作（通知，不阻塞）**；阻塞条件收敛到三件事——阶段内原子任务数 > 6、预计文件数 > 15、阶段范围相对已确认的拆分发生变化。三者之外直接派单，用台账与心跳保证可见性。

## 3. 阶段规模的两个维度

只看任务数会漏掉大任务：一个「重构鉴权模块」的任务可能涉及 30 个文件，放进阶段后上下文同样爆炸。因此同时卡任务数 3~6 与文件数 ≤ 15，任一超限即拆阶段。

## 4. 阶段级快照与失败定位

默认按阶段冻结一次基线快照与完整差异，把重复序列化从 N 次降到每阶段 1 次。代价是失败定位变贵：5 个任务一起测，FAIL 后不知道是谁引入的。因此约定失败时回退到单任务补丁级快照做定向复测，不允许开发者凭印象猜测归因。

配套约束：阶段内任务不得破坏彼此的验收项；强依赖的任务不放入同一阶段，依赖顺序写入阶段简报。

## 5. 证据不足三分流：防止验证责任转移给负责人

把证据不足一律「视为完成、记入汇报」的本质是把验证责任转移给负责人——但负责人不是执行者，没有上下文判断某个未验证项是否危险，累积若干 change 后汇报文件会退化为免责声明。

因此按影响面三分：

| 分类 | 判据 | 处置 |
| --- | --- | --- |
| 影响主流程 | 主要路径不可用或结果不可信 | 必须补证，同一任务同一快照**最多一次**，第二次仍无法判断即停止补证并上报 |
| 影响边缘路径 | 次要分支、异常分支、非关键字段 | 不补证，进汇报文件，可继续交付 |
| 不影响功能 | 日志、文案、风格、可观察但不影响行为 | 不补证，进汇报文件，该任务视为完成 |

## 6. 可证伪闸门是自修的唯一前置护栏

阶段派单加阶段级快照以后，**阶段内事实上只有开发者在动代码**，测试者到阶段末才介入——这等于已经把「自测自修」变成了现实。若不同时设立护栏，状态就是「完整自修权 + 零防作弊机制」，风险高于原先的逐任务模式。

护栏取最小集：**固定 acceptance 必须可证伪**。理由在于测试者是全新上下文，只持有终态代码，其判断力上限等于 acceptance 的可证伪程度——

- acceptance 写明「返回 200 且含字段 X」时，断言被放宽到 `status < 500`，测试者对照即可判 FAIL；
- acceptance 写「接口正常响应」时，测试者没有基准，只能判断测试与实现是否自洽，此时放宽断言等于修改标准，任何角色都无法发现。

因此 acceptance 粒度是真正的闸门，其余留痕类手段是次优补丁。本次只落地闸门本身，留痕双投递等观察后再定。

## 7. 明确不做

- **并行派单**：多实例写入共享工作区存在文件冲突与 git 写操作竞争风险，收益不确定，先不做。
- **Git worktree**：可解决并行隔离，但引入依赖复制、本地配置、端口、清理安全五项配套，且本机 git 存在清理目录树的历史异常，先不做。

## 8. 风险

| 风险 | 处置 |
| --- | --- |
| 批量下发导致回执覆盖不全、偷懒 | 回执按任务 ID 分段，禁止整体总结，缺一段即视为该任务未交付 |
| 阶段末一次读多份证据，管理者认知负荷上升 | 依赖图与验收总表写入阶段简报；判定按 ID 逐项，不合并 |
| 阶段内任务互相破坏验收项 | 强依赖任务不进同一阶段；阶段交付前执行整体回归 |
| 阶段 3~6 与文件数 15 的上限未实测 | 首次生效，在第一个真实 change 上观察后调整 |
| `docs/handoff/` 进入版本库 | 本次不加入 `.gitignore`，待实际产出后确认是否需要忽略 |
