# Proposal

## Why

负责人只在异常上报和收尾总结时被告知，无法看到任务如何拆分、派发给谁、当前处于什么状态；同时「一次只派一个原子任务」使每个任务都要重复走一遍完整的交接链路，往返次数随任务数线性增长，一个中等规模 change 会产生上百次往返。此外缺少阶段级交付与部分通过机制，单个任务失败会拖住整个阶段。

## What Changes

- 阶段派单：一个阶段一次派发，包含 3~6 个原子任务且预计文件数不超过 15，超出即拆分为多个阶段；开发者按阶段内顺序实施，完成后一次性交付回执
- 阶段门：每阶段派单前提交阶段简报（目标任务、依赖与顺序、契约与约束、项目经验与陷阱、验收总表、预计文件数）；**默认不阻塞**，仅当任务数超过 6、文件数超过 15 或阶段范围发生变化时才须负责人确认
- 负责人可见性：派发台账 `docs/handoff/<change-id>/dispatch-log.md`、阶段任务清单 `<stage>-tasks.md`（验收项与任务 ID 绑定）、每阶段判定后的心跳
- 阶段级快照：一个阶段冻结一次基线快照与含未跟踪新增文件的完整差异，失败时才回退单任务补丁级做定向复测
- 流程分级：L0／L1／L2，排除式判据；L0 免 `design.md` 与 `specs` delta
- 部分 PASS 与阶段末判定表：通过的任务先交付，未通过的单独进下一轮，逐任务逐项记录不合并判定
- 证据不足按影响面三分流：影响主流程的必须补证且同一任务同一快照最多一次；影响边缘路径与不影响功能的两类进未验证项汇报文件 `docs/handoff/<change-id>/unverified.md`，收尾时由总管向负责人逐项说明
- 回执按任务 ID 分段，禁止整体总结，缺一段即视为该任务未交付
- 固定 acceptance 必须可证伪，「正常」「可用」「合理」「无误」等不得作为唯一验收项

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `agent-development-workflow`：新增阶段派单与阶段门、负责人可见性、阶段任务清单与验收项约束、阶段级快照与部分 PASS、证据不足分级处置、流程分级；修改任务派发粒度与回执格式要求。

## Impact

- 协作规则文档：`AGENTS.md`、`AGENTS_manager.md`、`AGENTS_rules.md`
- 新增交接目录约定 `docs/handoff/<change-id>/`（台账、任务清单、判定结果、未验证项汇报）
- 不影响项目代码、数据库、CI/CD 或公开 API；`AGENTS_test.md` 本次不修改
