# Delta for agent-development-workflow

## ADDED Requirements

### Requirement: 阶段派单与阶段规模
总管 MUST 以阶段为单位派发开发任务；一个阶段 MUST 包含 3~6 个原子任务且预计文件数不超过 15，任一超限 MUST 拆分为多个阶段。开发者 MUST 按阶段内的执行顺序实施全部任务，并在全部完成后一次性交付回执。

#### Scenario: 阶段规模超限
- **WHEN** 拆出的阶段原子任务数超过 6，或预计文件数超过 15
- **THEN** 总管拆分为多个阶段，不得一次性派发该批任务

#### Scenario: 强依赖任务同阶段
- **WHEN** 两个原子任务之间存在接口、数据或迁移依赖
- **THEN** 二者不放入同一阶段，且其依赖顺序写入阶段简报

### Requirement: 阶段门与负责人可见性
每阶段派单前 MUST 向负责人提交阶段简报，内容含阶段目标、任务清单、依赖与执行顺序、契约与约束、项目经验与已知陷阱、验收总表及预计文件数。提交后默认继续派单、不等待回复；仅当阶段内原子任务数超过 6、预计文件数超过 15，或阶段范围相对已确认拆分发生变化时，MUST 获得负责人确认后才派发。派发任一阶段或任务 MUST 同时向 `docs/handoff/<change-id>/dispatch-log.md` 追加台账行，并在每阶段判定后以及阶段内出现 BLOCKED、升级或范围变化时向负责人发送一行心跳，心跳 MUST NOT 阻塞流程或等待回复。

#### Scenario: 规模未超阈值
- **WHEN** 阶段简报已提交且任务数与文件数均未超过阈值、范围无变化
- **THEN** 总管直接派单，不等待负责人回复

#### Scenario: 规模或范围超阈值
- **WHEN** 阶段内原子任务数超过 6、预计文件数超过 15 或阶段范围发生变化
- **THEN** 总管停止派单并获得负责人确认后才继续

#### Scenario: 台账与心跳
- **WHEN** 任一任务被派发或阶段判定完成
- **THEN** 台账同一行更新状态而不新增重复行，且向负责人发出一行心跳；台账不得包含密钥、令牌、公网地址或个人数据

### Requirement: 阶段任务清单与验收项约束
每阶段派单 MUST 同时生成任务清单文件 `docs/handoff/<change-id>/<stage>-tasks.md`，每个原子任务一段并写入与其 ID 绑定的固定验收项；验收项一经写入 MUST NOT 随对话漂移。固定 acceptance MUST 可证伪，含具体值、状态码、字段名、边界条件或可观察输出；「正常」「可用」「合理」「无误」「符合预期」等不可证伪表述 MUST NOT 作为唯一验收项，总管派单前 MUST 自查并退回重写。开发者回执 MUST 按任务 ID 分段，禁止写成整体总结。

#### Scenario: 验收项不可证伪
- **WHEN** 某任务的固定 acceptance 仅由「正常」「可用」「合理」等不可证伪表述构成
- **THEN** 总管退回重写该验收项，不得以此派单

#### Scenario: 回执写成整体总结
- **WHEN** 开发者回执未按任务 ID 分段，或缺少某个已派发任务的段落
- **THEN** 该缺失段落对应的任务视为未交付，不得进入测试阶段

### Requirement: 阶段级快照与部分 PASS
快照与完整差异默认 MUST 按阶段冻结：一个阶段内多个原子任务均通过开发自检后，为该阶段冻结一次基线快照并生成包含未跟踪新增文件的完整差异；出现失败时 MUST 回退到单任务补丁级快照做定向复测。阶段末 MUST 允许部分任务 PASS 并直接交付，未通过的任务单独进入下一轮修复，MUST NOT 因单个任务失败判定整个阶段未完成。阶段验收后 MUST 逐任务、逐验收项记录判定结果且不合并判定。

#### Scenario: 阶段内全部任务自检通过
- **WHEN** 阶段内所有原子任务均通过开发自检
- **THEN** 总管为该阶段冻结一次基线快照与完整差异，测试按阶段验收全部任务

#### Scenario: 阶段内有任务失败
- **WHEN** 阶段验收出现失败项
- **THEN** 回退到单任务补丁级快照做定向复测，且不得由开发者凭印象猜测归因

#### Scenario: 阶段末部分通过
- **WHEN** 阶段末部分任务通过而部分未通过
- **THEN** 通过的任务交付并勾选，未通过的任务单独进入下一轮，判定表逐项记录而不合并

### Requirement: 证据不足分级处置
测试结论为证据不足时 MUST 按影响面分三类处置：影响主流程（主要路径不可用或结果不可信）MUST 补证且同一原子任务、同一快照最多补证一次，第二次仍无法判断 MUST 停止补证并上报，不得再派发该任务验证；影响边缘路径（次要分支、异常分支、非关键字段）MUST NOT 补证，记入未验证项汇报文件后可继续交付；不影响功能（日志、文案、风格、可观察但不影响行为）MUST NOT 补证，记入汇报文件且该任务视为完成。汇报文件 MUST 位于 `docs/handoff/<change-id>/unverified.md`，逐项记录未验证项、所属任务 ID、影响面分类、判断依据与建议补验方法；收尾时总管 MUST 读取该文件并向负责人逐项说明。

#### Scenario: 影响主流程且可补证
- **WHEN** 证据不足涉及主要功能路径且尚未超过一次补证
- **THEN** 总管更换验证方法或补齐前提后补证一次并记录与上次验证的差异

#### Scenario: 影响主流程且已补证一次
- **WHEN** 同一任务同一快照已补证一次仍无法判断
- **THEN** 停止补证并上报负责人，不得再次派发该任务的验证

#### Scenario: 边缘或不影响功能
- **WHEN** 证据不足仅涉及边缘路径或完全不影响功能行为
- **THEN** 不补证，记入未验证项汇报文件，相关任务按记录的范围继续交付

### Requirement: 流程分级
改动 MUST 按判据分为三级：**L0** 仅限文档、脚本、整理类改动，免 `design.md` 与 `specs` delta，保留 proposal 与 tasks；**L1** 为标准流程，保留全套工件；**L2** 涉及对外契约、数据库迁移、CI/CD、公开 API 或权限模型，保留全套工件并额外记录影响面与回滚方案。分级判据 MUST 为排除式：凡不能明确排除对外契约、数据库、数据库迁移、CI/CD 与公开 API 影响的改动 MUST NOT 判为 L0。

#### Scenario: 判定为 L0
- **WHEN** 改动仅限文档、脚本或整理，且可明确排除对外契约、数据库、CI/CD、公开 API 影响
- **THEN** 只产出 proposal 与 tasks，不产出 design 与 specs delta

#### Scenario: 不能明确排除关键影响
- **WHEN** 无法明确排除对外契约、数据库、CI/CD 或公开 API 影响
- **THEN** 一律判为 L1 或 L2，不得按 L0 简化工件
