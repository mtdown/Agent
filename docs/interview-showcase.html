M4

RAG 检索链路

核心亮点权限过滤 · 三路召回 · RRF · 重排

核心职责：一次查询 → 权限过滤 → 文号精确钉位 → 向量 + BM25 双通道召回 → RRF 融合成候选池 → 语义重排 → 返回 top-6 证据，并输出分步耗时。

业务流程
用户提问 ├─ 1. 权限过滤 effectiveSpaceIds = 可见空间 ∩ 请求空间 → 空则直接返回（零泄漏） ├─ 2. 文号钉位 正则抽公文号 → docNumber 精确命中组（score=1.0），组上限 200 ├─ 3. 查询分支 默认仅原问题；可选多查询（改写 0.7 / 假设答案 0.6） ├─ 4. 双通道 向量通道（余弦，池深 50） + BM25 通道（CJK bigram，池深 50） ├─ 5. RRF 融合 按名次融合（k=60，取文献默认值，不针对评测集调参）→ 融合池 50 ├─ 6. 证据合并 同文档相邻块合并（默认关） ├─ 7. 语义重排 融合池 → qwen3.7-text-rerank → 截断 top-6（失败降级融合序） └─ 8. 组装 钉位组占前排槽位，重排结果填剩余槽位

技术难点与解决方案（每个都带实测数字，这是本模块最值钱的部分）
  • 难点 1：权限泄漏必须为零。 方案：不"检索后再过滤"，而是先算 effective = 可见 ∩ 请求，向量库与 BM25 只拿到这个集合，模型永远没有机会看到越权内容。 验证：D 类 10 题用成员 / 非成员双 API Key 对照，leakCount = 0。
  • 难点 2：公文文号在纯向量下几乎不可分（"〔2026〕66 号" vs "〔2026〕67 号"）。 方案：加规则层精确命中，命中组 score=1.0 高于一切余弦值，钉位在前排。 验证：B 类 9 题 docRecall@6 = 1.000、hitRate@6 = 1.000。
  • 难点 3（第二层坑）：钉位组不能进 RRF 融合。 实测把钉位组混进融合后，B 类 oracle@50 从 0.7506 摊薄到 0.4129，端到端还要再掉约 24pt ⇒ 改成"钉位组独立占槽 + 组内按相关性重排"。 另一处同源缺陷：早期精确层满额后会整段跳过向量检索，等于"只返回位置最靠前的 topK 块"，已修。
  • 难点 4：余弦相似度和 BM25 不在同一量纲，不能直接加权。 用 RRF 按名次融合（1/(k+rank)）。k 取文献默认 60 且刻意不用评测集调参——这样对外声称的收益才是干净的。
  • 难点 5：池深怎么定？ 实测四档：深度 20 → oracle 0.7690 / 实测 0.7590；深度 50 → 0.8600 / 0.7930（mean 516ms，p95 600ms）；深度 100 → 0.9061 / 0.8030（mean 720ms，p95 928ms）。重排精度随池深衰减（吃到上限 98.7% → 92.2% → 88.6%），50→100 只多 1.0pt 却多 190ms ⇒ 默认定 50。
  • 难点 6：外部模型依赖不能拖垮主链路。 重排失败捕获异常后回退融合序；未运行的通道耗时记 null 而不是 0（避免误导成"很快"），前端按分步时间线渲染。
  • 难点 7：开关类优化会"静默无效"。 多查询、证据合并这类功能打开后如果没实际生效（比如分支没生成、没有可合并块），输出会和输入一模一样而指标照常出数 ⇒ 强制打日志自证（分支数 / 合并块数），区分"没效果"和"没生效"。
  • 难点 8：怎么知道天花板在哪？ 写诊断脚本算 oracle（该池深下完美重排的理论上限）。结论：池深 50 的 oracle 是 0.8600，实测 0.7930，未兑现的 18.52pt 里 73.3% 属于"池里已有、重排没排进 top-6" ⇒ 主瓶颈是段落级排序，不是"基础召回不足"。这一步把"继续加深度"这个错误方向直接否掉了。

技术难点与解决方案
  • 难点 1：gold 锚点绑什么？ 绑逻辑坐标 docId + chunkIndex，禁止绑数据库主键 chunkId。因为索引重建是"旧行置 INVALID + 插新行"，重建后同一逻辑块会拿到全新主键，绑主键的 gold 会全部失效。
  • 难点 2：防 gold 幻觉。 标准答案始终来自人类文本（LLM 只负责把官方解读"翻译"成问题）；每题 gold[].quote 必须程序校验逐字存在于该 chunk（quote_hit），这是唯一自动防线。
  • 难点 3：混算 overall 会被题型配比污染。 强制分组看：单文档 235 题 0.864 / 跨文档 89 题 0.809 / 配对 54 题 0.439 / 文号 9 题 0.685。跨版本比较必须同组比，否则改个出题配比就能"刷高"指标。
  • 难点 4：多大差异才算改进？ 连续两次同数据重跑 recall@6 极差 0.13 个百分点 ⇒ 把它作为数值可信下限，小于 0.2pt 的差异不作为改进证据。
  • 难点 5：抬答案集 K 不算达标。 recall@k 对 k 单调不减，所以 recall@10 = 0.8515 只是换口径；实测仅 14% 的题受益、证据密度从 19.3% 掉到 13.7%，而 docRecall@10 = 0.9674 已近饱和 ⇒ 对外只用 pool=50 的 recall@6。
  • 难点 6：把评测集本身当工程对象迭代。 先用置信区间量化"考卷够不够用"，再定位根因——发现出题只在标题书名号里找政策名，159 篇解读类只配上 31 对。放宽到正文匹配后：配对 31 → 150，文档覆盖 17% → 85%，切片覆盖 15.3% → 27.6%，置信区间收窄到 ±11.2%。
  • 难点 7：切块粒度会污染指标本身。 把评测单元从"单个 chunk"改成"连续证据区"，全体 recall@6 从 0.7930 → 0.8533，而单文档 / 跨文档（占 81%）几乎不变 ⇒ 说明不是放水，是修正了度量失真。结论：任何切块改动前必须先让评测与切块解耦。
  • 难点 8：泛化性检验。 另开英文 MultiHop-RAG 赛道（609 篇新闻 / 2556 题），自带脚本与结果目录，只共享打分内核，避免两套数据的指标定义各说各话。

技术难点与解决方案

  • 难点 2：切片失效策略。 "旧行置 INVALID + 插新行"而不是物理删——回收站恢复时可以按 contentVersion 直接翻转回来，版本漂移了才重建。
  • 难点 3（红线）：非 Markdown 会零切片且静默。 contentFormat != markdown 直接跳过索引（设计如此），所以导入链路必须兜底设成 markdown，否则文档存进去了却永远检索不到，且不报错。

  • 难点 5：重建时语言要取文档记录的 language，不能重新检测。 重新检测可能选到另一套 profile，导致所有 chunk 重新编号、已绑定的评测锚点全部失效。

A. 项目介绍类

Q1必背用两分钟介绍一下这个项目

按"背景 → 我做了什么 → 怎么证明有效 → 边界"四段讲。

  • 背景：企业知识库常见的痛点是"文档存下来了但找不到、找到了不敢信"。我想做的不是又一个聊天机器人，而是让知识可检索、可追问、可溯源。
  • 我做了什么：两阶段。第一阶段是 Wiki 知识库本体（多空间、Markdown 编辑、权限、回收站）；第二阶段在它上面建完整 RAG 链路——文档切片向量化、权限过滤检索、AI 流式问答、开放检索 API。
  • 怎么证明有效：建了 423 题评测集，recall@6 从 0.5623 提到 0.7930（+23.1pt），文档级与段落级召回的差距从 30.7pt 收窄到 12.9pt——说明优化真正作用在段落定位而不只是把文档捞回来。
  • 边界：这是个人技术展示项目，没有真实线上流量；规模是 216 篇 / 2061 块，向量检索用内存暴力余弦，量大了要换 ES 或 Milvus——接口已经抽象好了，换 Bean 即可。
收口数字：recall@6 0.7930 · docRecall@6 0.9223 · mrr 0.6262 · 权限泄漏 0 · 单并发 mean 516ms / p95 600ms。
Q2必背这个项目最难的/你最得意的部分是什么？

答"用评测反推优化方向"，不要答"接了大模型"。

  • 难在判断瓶颈在哪。基线出来后我看到 docRecall@6 远高于 recall@6，判定瓶颈在段落定位而不是文档召回；优化后两者落差从 30.7pt 收窄到 12.9pt，验证了诊断方向是对的。
  • 更得意的是"量化可信下限"。我连续两次跑同一份数据，recall@6 极差 0.13 个百分点，于是把它定成数值可信下限——小于 0.2pt 的差异我不当成改进证据。这让我能区分"真的变好了"和"只是抖动"。
  • 还有一条：我先算天花板再优化。池深 50 的 oracle（完美重排的理论上限）是 0.8600，实测 0.7930，未兑现的 18.52pt 里 73.3% 属于"池里已有、重排没排进 top-6"。这一步直接否掉了"继续加深候选池"这个方向——因为边际兑现率 50→100 只有 21.5%，加 190ms 只换 1.0pt。
四档池深实测：20 → oracle 0.7690 / 实测 0.7590；50 → 0.8600 / 0.7930（516ms）；100 → 0.9061 / 0.8030（720ms）。
Q3加分为什么不用 LangChain / LlamaIndex 或者现成的向量库？

这是个价值观问题，答"可控"和"可测"。

  • 我的目标不是最快跑通 demo，而是搞清楚每一段链路各自贡献多少。框架把融合、重排、切块都封装了，我就没法回答"这一段值不值"。
  • 自研之后我才能做 oracle 分析——把重排换成"完美重排"算天花板，从而知道 73.3% 的缺口来自排序而非召回。这个结论用黑盒框架是拿不到的。
  • 但我并没有排斥替换：VectorStore 是接口，现在是内存暴力余弦实现，量大了换 ES / Milvus 只换 Bean。骨子里是"先用自研把参数摸清楚，再决定要不要换"。
  • 补充一个诚实的点：依赖少也有代价——BM25 是我自己写的 CJK bigram，没有专业分词器的能力；规模上 2061 块够用，百万级就得换。

Q4必背完整讲一遍检索链路，每一段为什么这么设计

按"权限 → 规则 → 召回 → 融合 → 精排"五段讲，每段带一句理由。

  • ① 权限过滤先做。effective = 可见空间 ∩ 请求空间，向量库和 BM25 只拿到这个集合。不是检索完再过滤——那样模型已经看到越权内容了。
  • ② 文号规则层。公文文号在纯向量下几乎不可分（"〔2026〕66 号" vs "67 号"），所以加精确命中，score 置 1.0 高于一切余弦值。
  • ③ 双通道召回。向量通道负责语义，BM25 通道（CJK bigram）负责字面精确匹配。单靠向量时，gold 块经常排在 top-K 之外。
  • ④ RRF 融合。余弦和 BM25 量纲不同，不能直接加权，所以按名次融合 1/(k+rank)。k 取文献默认 60 且不用评测集调参。
  • ⑤ 语义重排。融合池 50 条交给 cross-encoder 精排截断 top-6。
BM25 通道的价值有实测：候选池 oracle@50 从 0.8148 抬到 0.8600。文号层：B 类 9 题 docRecall@6 与 hitRate@6 均为 1.000。
Q5必背为什么用 RRF 而不是加权求和？

核心是"量纲不可比"+"不引入需要标定的参数"。

  • 余弦相似度落在 [-1,1] 且分布集中，BM25 是无上界的累加分——两者不在一个尺度上，加权求和必须先归一化，而归一化系数需要在本语料上标定。
  • RRF 只用名次（1/(k+rank)），天然跨通道可比，不需要任何标定。
  • 我把 k 留在文献默认值 60 且刻意不用评测集调它——一旦调了，我对外声称的 +23.1pt 就混进了"针对考卷调参"的成分，收益就不干净了。这是我主动选择的取舍：宁愿少一点指标，也要结论可信。
Q6必背候选池深度为什么定 50？

这是"用数据做取舍"的标准答案，一定要把三档数字背下来。

  • 重排只能重排池子里已有的东西，所以池深决定 recall 的理论上限（oracle）。
  • 我测了三档：深度 20 → oracle 0.7690 / 实测 0.7590；深度 50 → 0.8600 / 0.7930；深度 100 → 0.9061 / 0.8030。
  • 关键观察是重排精度随池深衰减：实测吃到的天花板比例 98.7% → 92.2% → 88.6%。也就是说池越深，重排"从 N 里挑 6"越挑不准。
  • 所以 50→100：oracle 多 4.6pt，实测只多 1.0pt，代价是 mean 从 516ms 涨到 720ms（+190ms）。不划算，定 50。
延迟结构：深度 50 = mean 516ms / p95 600ms；深度 100 = mean 720ms / p95 928ms（同一 120 题取样、单并发、客户端端到端）。
Q7加分你怎么定位"瓶颈到底在召回还是在排序"？

答 oracle 分析（把排序器换成"完美排序"看上限）。

  • 方法：写诊断脚本，对同一批候选池用 gold 直接做"完美重排"，算出该池深下的理论上限（oracle），再和实测对比。
  • 结果：池深 50 的 oracle 是 0.8600，实测 0.7930，缺口 18.52pt。把这 18.52pt 拆开：73.3% 属于"池里已经有、重排没排进 top-6"，只有约 27% 是"池里根本没有"。
  • 结论：主瓶颈是段落级排序，不是基础召回不足。
  • 由此否掉的错误方向：继续加深候选池。边际兑现率 20→50 是 37.5%，50→100 只有 21.5%。
  • 另一条同源结论：真正的变量不是题型而是 gold 段落数。399 题全部是单文档；gold≥3 段的 64 题（16% 题量）贡献了 55.2% 的缺口，而单段题 237 题（59.4%）已经做到 0.9494。
Q8加分切块策略怎么定的？有没有踩坑？

讲"按标题层级切 + 中英双档参数 + 一个反直觉的发现"。

  • 基本策略：按 Markdown 标题层级切块，保留 heading path；超长小节按段落再切，过短小节向前合并，相邻块带重叠（中文 80 字符）避免上下文被切断。
  • 坑 1：中英不能共用一套参数。英文新闻段落常 800–1030 字符，中文 600 的上限会把它机械切断、切在单词中间 ⇒ 抽 ChunkerProfile：中文 600 / 重叠 80 / 句末"。；"，英文 1800（token 质量等价）/ 重叠 100 / 句末".!?;"，并识别 Mr.、e.g. 这类缩写和 U.S. 首字母缩写，保证不切碎单词和数字。
  • 坑 2：语言判定必须确定。纯函数、不问模型，所以重索引结果可复现。而且重建时要读文档记录的 language，不能重新检测——重检测可能选到另一套 profile，导致所有 chunk 重新编号、已绑定的评测锚点全废。
  • 坑 3（最重要，反直觉）：切块粒度会污染指标本身。把评测单元从"单个 chunk"改成"连续证据区"后，全体 recall@6 从 0.7930 → 0.8533，但单文档 / 跨文档（占 81%）几乎不变 ⇒ 说明不是放水，是修正了度量失真。结论：任何切块改动前必须先让评测与切块解耦，否则你分不清是系统变好了还是尺子变了。
Q9加分权限过滤是怎么保证零泄漏的？
  • 设计原则：权限是检索的前置条件，不是后置过滤器。先算 effective = 用户可见空间 ∩ 请求空间，向量通道和 BM25 通道只拿到这个集合，模型永远没有机会看到越权内容。
  • 开放端点也不开后门：X-API-Key 解析出 owner 之后，走的是与站内完全相同的服务层，所以权限逻辑零分叉，不存在"外部接口漏权限"。
  • 怎么验证：D 类题用成员 / 非成员两个 API Key 做镜像对照，leakCount = 0。泄漏指标是一票否决，不进 overall 平均——因为平均值会把"漏得少"美化成"没漏"。
10 题权限镜像：leakCount 0 / leakRate 0.0 / leakedIds 空。
Q10加分幻觉怎么控制？拒答怎么做？
  • 控制幻觉的手段：① system prompt 明确"资料不足以回答时明确说明未能找到依据，不得编造"；② 文号只能出现在资料标注里，禁止编造；③ 引用元数据全部走 meta 事件下发，前端不信任 LLM 文本里出现的任何文号。
  • 拒答现状（诚实）：唯一的硬拒答触发点是 hits.isEmpty()。
  • 为什么没做"相关度阈值拒答"：数据否决了。有答案题的 top1 分数最低 0.4169，无答案题最高 0.6153——两段分布重叠，不存在能一刀切的阈值。实测权衡：若阈值设到能拦住 100% 无答案题，会误杀 32% 的有答案题。所以拒答必须放到答案层做，检索层单阈值这条路走不通。
  • 另一个诚实点：我试过用 LLM-as-Judge 评 faithfulness，实测精准率只有 6% ⇒ 不能当判据。现在只用四项零成本指标：引用覆盖率 / 误拒率 / 拒答正确率 / 文号合规率。
陷阱提醒：如果面试官追问"那你的拒答准确率是多少"，不要编。中文答案层至今没有"正确率"这个口径（没有可靠判官），只有上述四项零成本指标。
Q11加分换更强的生成模型能解决问题吗？

这题是送分题——答"不能，我有数据"，直接体现你不被"换大模型"这种直觉方案带跑。

  • 我在英文 MHR 数据集 100 题上做了对照：qwen3.8-max 非思考档正确率 +7pt，但 McNemar p = 0.1671，不显著。
  • 更关键：INCORRECT 从 20 道变成 20 道，一道都没修好——只是换了一批错题。
  • 还付出了代价：实质未答率 5.68% → 20.45%（显著恶化，p=0.0029），引用覆盖率 −8.2pt，耗时 ×1.99。
  • 结论：瓶颈既不在 prompt、也不在生成模型，在检索层。
补充一个方法论上的自我约束：该实验的判官（qwen3.8-flash）和回答模型（qwen3.8-max）同家族，所以那 +7pt 要打折看——我会主动说明这个实验设计的局限。
同源结论：prompt 的可靠作用域是措辞不是判断。我试过在 prompt 里下发相关度信号 + 两态指令，无可测增益。

C. 评测与数据驱动类（差异化竞争力）

Q12必背评测集是怎么建的？gold 怎么标？
  • 规模与构成：423 题 / 七类题型（单文档 235、跨文档 89、配对 54、无答案 14、合成 12、权限 10、文号 9），其中 399 题计分。
  • gold 绑逻辑坐标而非主键：docId + chunkIndex，禁止绑 chunkId。因为索引重建是"旧行置 INVALID + 插新行"，重建后同一逻辑块拿到全新主键，绑主键的 gold 会全部失效。
  • 防标注幻觉：标准答案始终来自人类文本，LLM 只把官方解读"翻译"成问题；每题 gold[].quote 必须程序校验逐字存在于该 chunk（quote_hit），这是唯一自动防线。
  • 全程只读：脚本不写业务库、不改后端、不触发索引重建，执行前后 wiki_chunk 恒为 2061 行全 ACTIVE。
覆盖度：文档覆盖 37/216（17%）→ 183/216（85%），切片覆盖 15.3% → 27.6%。
Q13必背指标怎么选？为什么必须分组看？
  • 四个主指标：recall@6（段落级召回，主口径）、docRecall@6（文档级）、mrr（排序质量）、hitRate@6（至少命中一条）。再加权限泄漏（一票否决）。
  • 必须分组的原因：题型难度差异极大——单文档 0.864 vs 配对 0.439（相差 42pt）。混算 overall 会被题型配比直接污染：改一下出题比例就能"刷高"指标。所以跨版本比较必须同组比。
  • 不用 recall@10 当主口径：recall@k 对 k 单调不减，所以 recall@10 = 0.8515 只是换口径不算改进。实测仅 14% 的题受益、证据密度从 19.3% 掉到 13.7%，而 docRecall@10 = 0.9674 已近饱和。
分组基线：单文档 235 题 0.864 · 跨文档 89 题 0.809 · 配对 54 题 0.439 · 文号 9 题 0.685（docRecall@6 = 1.000）。
Q14加分怎么判断一次改动是真的有效还是抖动？
  • 先量化抖动本身：同一份数据连续跑两次，recall@6 极差 0.13 个百分点 ⇒ 这就是本评测的数值可信下限。
  • 定规则：小于 0.2pt 的差异不作为改进证据。这条规则救过我好几次——有几次"涨了"其实就是噪声。
  • 再看统计显著性：答案层对照用 McNemar 检验（如换模型那次 p=0.1671 不显著），不要只看百分点差。
  • 还要防"静默无效"：多查询、证据合并这类开关功能，如果没实际生效（分支没生成 / 没有可合并块），输出会和输入一模一样而指标照常出数 ⇒ 强制打日志自证分支数 / 合并块数，区分"没效果"和"没生效"。这个坑我踩过一次。
Q15加分有没有改过评测集本身？为什么？

这题很能区分"跑过评测"和"建过评测"。

  • 改过，而且理由是先量化再定位：先用置信区间判断"考卷够不够用"，发现样本不足以分辨差异。
  • 根因定位：出题逻辑只在文档标题的书名号里找政策名，导致 159 篇解读类只配上 31 对（128 篇媒体视角的只中 4 篇）。
  • 修复：放宽到正文匹配 ⇒ 配对数 31 → 150，文档覆盖 17% → 85%，可分辨样本 29 → 76，置信区间收窄到 ±11.2%。
  • 心法：把评测集本身当工程对象迭代，而不是一次性产物。考卷不可信的时候，任何指标都没有意义。
  • 泛化检验：另开英文 MultiHop-RAG 赛道（609 篇新闻 / 2556 题），自带脚本与结果目录，只共享打分内核——刻意让两套数据共用同一份"怎么量"，防止指标定义各说各话。

D. 工程实现类

Q16索引为什么不用定时任务全量重建，而用事件驱动？
  • 时效性：文档保存后立刻可检索，不等调度窗口。
  • 正确性：用 @TransactionalEventListener(phase = AFTER_COMMIT)，保证不会读到未提交的数据；fallbackExecution = true 兜底无事务场景。
  • 不阻塞写路径：异步线程池 ragIndexExecutor（核心 2 / 最大 4 / 队列 200）；索引失败只记日志，绝不影响文档保存。
  • 生命周期完整：9 种变更类型各有处理（创建/更新/逻辑删/恢复/物理删/移动/空间逻辑删/空间恢复/空间物理删），并有孤儿 chunk 对账兜底。
  • 缓存一致：切块变更后同时失效向量快照与 BM25 倒排（单一通知点），否则词法通道会继续吐已删文档的内容。
Q17SSE 流式有哪些坑？
  • 必须显式 complete。不调 emitter.complete() 连接会挂到 120s 超时，前端 await 永不 resolve。
  • 客户端断开要真的停。onCompletion / onTimeout 里 future.cancel(true) 中断还在流的 LLM 调用。
  • 编排要可单测。抽 EventSink 接口，SSE 只是适配器，不需要真实 HTTP 就能测问答流程。
  • 前端流式重渲染。Vue3 的 Proxy 会被绕过，delta 不触发重渲染（文字积压、点一下才整段蹦出）⇒ 消息对象用 markRaw。
  • 可观测性。done 事件带分步耗时时间线（permission / docCount / docNumber / embed / vector / rerank / firstToken / llm），前端可展开。没有这个，我根本做不出 oracle 分析。
  • 零命中短路。hits 为空直接回拒答文案，llmMs = 0，不浪费一次模型调用。
Q18外部模型调用失败怎么办？
  • 分层降级：重排是可选通道，失败捕获异常后回退融合序，绝不把请求打挂；embedding 不可用时索引降级、靠回填和对账兜底。
  • 重试要有依据：embedding 是幂等 POST 可安全重试（1 次原始 + 2 次，300ms/1000ms 退避）。原因很具体——云端网关会静默回收空闲 keep-alive，空闲后第一发常踩死连接抛 Connection reset，重试即新建连接恢复。不重试就会对用户报错。
  • 不重试的场景：HTTP 层错误（鉴权 / 限流 / 参数）重试无益，直接抛。
  • LLM 只重试"首字之前"：已经吐出部分内容再重试会造成重复内容，所以首字后失败立即上抛。
  • 耗时记账诚实：没运行的通道耗时记 null 而不是 0，避免把"没跑"渲染成"很快"。

E. 反问与陷阱类

Q19必背这个系统现在最大的短板是什么？

主动暴露短板非常加分，但必须同时给出你定位到的根因——否则就是自曝其短。

  • 短板 1：答案层没有"证据充分性"判定。唯一硬拒答是 hits.isEmpty()。我已用数据证明检索层单阈值走不通（有答案题最低分 0.4169 < 无答案题最高分 0.6153，分布重叠），所以正解是把判定放到答案层——这是下一步第一优先级。
  • 短板 2：段落级排序仍是主瓶颈。池深 50 未兑现的 18.52pt 里 73.3% 属于"池里已有但没排进 top-6"。下一步方向：① 文档分组配额重排（先例是文号钉位组，零新模型依赖）；② 查询改写 / 多路召回；③ 切块（但必须先做评测解耦）。
  • 短板 3：中文答案层缺乏可靠判官。没有"正确率"这个口径，只有四项零成本指标；英文侧有 LLM 判官但精度存疑（同家族模型判自己要打折）。
  • 短板 4：规模。向量检索是内存暴力余弦，2061 块够用，量大了必须换 ES / Milvus（接口已抽象好）。
  • 已知 bug（主动提）：chunk.docNumber 取的是"正文里出现的文号"而非"文档自身的文号"，新闻稿引用公文号就会污染文号精确层。
Q20必背（陷阱）既然 recall@10 有 0.8515，为什么不把 topK 提到 10？

这是典型的"用换口径冒充改进"，必须当场识破。

  • recall@k 对 k 单调不减，抬 k 一定会涨，这不叫优化，叫换尺子。
  • 实测：仅 14% 的题受益；证据密度从 19.3% 掉到 13.7%（同样的 6 条里塞进更多无关内容，反而稀释 prompt）；docRecall@10 = 0.9674 已近饱和，说明"多给几条"解决不了剩下的问题。
  • 我的对外口径锁死在 pool=50 的 recall@6。
同类陷阱还有："换了个 embedding 模型指标涨了 0.15pt" → 低于 0.2pt 可信下限，不算；"这次跑出来比上次高" → 先看是不是同数据同配置。
Q21如果要上生产，你还会补什么？
  • 检索层：换专业向量库（ES / Milvus）+ 专业中文分词器；候选池与重排做异步并行；加结果缓存。
  • 答案层：补证据充分性判定与拒答；引入可靠的判官体系（人工标注金标 + 跨家族模型交叉验证）。
  • 工程：embedding 调用加限流与配额；重排超时熔断；检索链路加 traceId 全链路追踪；索引失败进死信队列而不是只记日志。
  • 评测：把评测接进 CI，任何改动自动跑回归并与基线对比，超阈值就报警。
