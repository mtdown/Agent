## 修改与限制

- 容器和网络均附本轮随机归属标签。创建返回非零时读取对应资源的标签和 ID；仅标签匹配时登记不可变 ID 并清理。未能确认归属时不删除，报告可能残留；创建失败的原异常保留。成功创建的资源也按返回 ID 清理；清理失败报告可能残留。
- 启动失败但代理已创建时按 ID 获取状态、退出码和日志；没有归属证明时不访问同名代理。日志按常见敏感字段过滤，不打印环境变量。**关键词过滤不能保证识别所有形式的未知秘密**；当前真实回归使用固定 nginx 镜像、受控配置和本地专用随机资源，不向容器注入凭据，输出不构成对任意日志的保密保证。
- 保留原配置验证、后端 IP 变化、未重启和路径断言；不改生产配置、工作流、依赖、服务或接口。

## A2 诊断补充（同一开发轮，交独立测试前）

针对上面关键词过滤无法保证未知秘密的问题，已替换为白名单结构化摘要：只展示已知容器状态及退出码、Nginx 已识别错误级别和固定类别、明确允许的两个配置路径与行号；未知日志正文隐藏。`nginx -t` 的 stderr 也进入相同摘要处理，以便定位已知配置错误。脚本顶层失败只输出固定错误类别，不序列化原始异常消息、stdout 或 stderr；内层仍抛出原始异常供测试断言。预检亦不输出原始异常。代价是未识别的具体错误文本不会显示。

先写随机无关键字秘密及配置 stderr 测试，分别观察旧实现泄漏和缺少配置诊断的红灯；现 `node --test deployProxyLifecycle.test.mjs` 退出 0，18 项通过。测试断言未知值不会从日志、异常消息和字段输出，已知 unknown-directive 的安全路径及行号可见，原始异常对象保留。顶层输出核验基于实际使用的 `reportFailure` 函数和脚本 catch 路径审查，未在子进程故障注入下运行完整脚本。再次运行 `node deployProxy.test.mjs` 退出 0，真实本机后端地址改变、代理未重启；`git diff --check` 退出 0。原 CI 故障原因仍未知，须独立复测。
